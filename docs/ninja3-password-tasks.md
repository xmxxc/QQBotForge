# #75 单账号任务接线（本地第二阶段）

本阶段基于协议提交 `c3e11992d14e76c28561cba207cfa517ab8cf4a0`，普通 merge 指定 #72 `129df14178d1f551b06bc131a73aacde74c30255` 后实现。仅本地离线交付候选，等待总控组合与独立审查；未推送、未部署、未真实登录或改密。协议原理见 [第一阶段说明](ninja3-password-protocol.md)。

## 主人入口与普通确认

- 群聊／私聊 `忍3改密`：默认未选，不提交；可选名称只在私聊列出，群内仅提示到私聊或后台查看。
- `忍3改密 名称`：选择单个账号，返回任务编号；不接收指定密码。同一选择者对未变化账号重复选择返回同一任务。
- `忍3确认 编号`：由同一选择者普通确认，才固定随机密码并启动。选择后账号记录改变会要求重新选择，不能确认过时目标。
- `忍3任务 编号`、`忍3取消 编号`、`忍3恢复 编号`：查询、取消和只补本地提交。均须当前主人；跨 Bot 引用不可用。群内仅简短回执，远端详细状态发主人私聊／已登录后台。
- `忍3重试 编号`（仅原选择者）、`忍3放弃 编号`：只用于远端“尚未提交”或“明确拒绝”的已结束任务。重试用同一密封意图（同一新密码）再走一次协议；放弃则释放暂停、保留原密码（远端确定未改）。未知结果两者都拒绝，等待 #76。
- 主人先在私聊发 `忍3` 登记通知地址。推送失败、未知或没有地址如实保留在任务的 notification 字段，不回复“已送达”。

后台复用现有会话鉴权、来源检查及 Bot 参数：

| 方法／相对 `/api/ext/ninja3/` | 请求 | 行为 |
| --- | --- | --- |
| GET `password-tasks?bot=...` | 无 | 本 Bot 公开状态清单，不含意图密文或凭据 |
| GET `password-tasks/{id}?bot=...` | 无 | 单任务状态 |
| POST `password-tasks?bot=...` | `{"account":"账号ID"}` | 明确选择，空值不默认选择 |
| POST `password-tasks/{id}/confirm?bot=...` | `{}` | 普通确认，仅后台自己选择的任务 |
| POST `password-tasks/{id}/cancel?bot=...` | `{}` | 首次请求取消；再次取消不重复打断清理 |
| POST `password-tasks/{id}/recover?bot=...` | `{}` | 仅恢复明确成功后的本地提交／未送达通知，不调用协议 |
| POST `password-tasks/{id}/retry?bot=...` | `{}` | 同一意图重试，仅后台自己选择且远端未提交／明确拒绝的任务 |
| POST `password-tasks/{id}/release?bot=...` | `{}` | 放弃远端未提交／明确拒绝的任务并恢复账号 |

后台是实际已鉴权 HTTP 入口，本轮没有新增页面控件。面板鉴权是单一主人会话，所有后台请求共用 `backend` 选择者身份；选择者区分的是 QQ 与后台、不同 QQ 主人之间。它不能借用 QQ 选择产生的确认引用；QQ 确认也不能借用后台选择。所有额外密码参数被拒绝。

## 状态、事务和恢复

`PasswordTasks` 使用同一个 ninja3.db 内的专用表，不是通用任务框架。选中状态不暂停、不生成密码；确认事务同时保存 Fernet 加密的固定意图、待用新密码与 active 暂停标记。意图绑定 Bot、账号与操作编号，解密后再次比对关联。默认密码从四位数字与 xmx／xc 的四种前后组合中选择，允许前导零；旧值相等则重取。相同意图重复确认／重启不再生成密码。

SQLite `BEGIN IMMEDIATE` 与 `(bot,account) WHERE active=1` 唯一索引共同约束多连接／多进程并发。已有任务会直接返回相同编号。未解决任务禁止修改该账号登录凭据或删除（后台返回409及明确原因，不报存储故障）；启用、开放群、说明等仍可编辑（删除群时去除引用不会半途失败），其他账户照常查询。账号写入对登录凭据做比较交换：调用方读到的凭据若已被改密本地提交改变，写入以409拒绝，不会用旧读取把新密码写回旧值。数据库升级为 user_version=2，旧 #72 v1 读取器会拒绝该库，避免回滚旧代码忽略任务暂停；部署回滚必须先处理活动任务或使用对应一致性备份，不能手改版本号绕过。

状态流：selected → prepared（固定意图／暂停已提交）→ preparing → submitting（持久化“可能已提交”）→ paused 或 completed。远端状态与本地提交分别记录：

执行权是持久的：工作协程不靠进程内 workers 字典或唯一索引判断能否继续，而是在三个事务里比较同一行的执行令牌 runner 与 active（前两处另核对 state 与取消标记），这三个事务就是线性化点：

1. 开始：仅当 active、未取消且 state=prepared、runner 为空时，原子改为 preparing 并写入本协程的新 runner。确认事务提交到协程真正开始之间若已被取消、放弃、重启转暂停或被另一个协程领走，迟到的 `_start` 在此失败，不登录、不写任务。
2. 改密提交前：`before_submit` 事务要求 runner 相同、active、state=preparing、未取消，才改为 submitting/unknown。在它之前提交的放弃、取消、重试或其他进程的初始化都会让它失败；在它之后任务远端为未知，放弃和重试都被拒绝。
3. 结果写入：只核对 runner 相同且仍 active，不要求 state，所以本执行器的确定结果在另一进程初始化把 submitting 转为暂停未知后仍能写入（同一意图，信息更准确）；放弃（active=0）、重试（清空 runner）、本地完成后的旧执行器结果直接丢弃，不改状态、不解除暂停、不改账号。

同一已确认意图因此最多一次被领走执行；放弃后新选择的任务是另一行，旧执行器无法领走或覆盖它。重试沿用同一密封意图，但清空 runner，上一轮迟到协程不能再提交或回写。

- 准备失败／取消且尚未发送：not_submitted，仍暂停；主人可同意图重试或放弃。
- 明确拒绝：rejected，仍暂停；主人可同意图重试或放弃。
- 已提交后超时／取消／无可靠响应：unknown，仍暂停，不能重发。未知登录核验归 #76。
- 明确成功：先记录 reported_success、local=pending，再将正式密码与 completed／取消本任务暂停放在同一事务中提交。失败保持 pending／暂停，恢复仅写本地。成功不清除启用范围、未来紧急标记或其他独立暂停来源。

远端结果确定后落盘失败（瞬时锁或磁盘错误）先在协程内有界重试7次，间隔0.2→10秒退避共约19秒；每次写入另受存储连接 SQLite 默认5秒忙等待限制，真实写锁下最坏约54秒，期间其他存储操作同样排队等待。仍失败时不丢弃结果：本进程把确定结果连同执行令牌保留在内存，任务公开 error 显示 `result_not_persisted`（存储可读不可写时可见；真实写锁下读取同样被拒，查看返回503，以日志为准），库内仍是 submitting/unknown，账号保持暂停，重试／放弃被拒绝。之后后台按30、60、120、300、600秒退避再写5次，不忙等、不阻塞业务入口；主人 `恢复`／后台 recover 随时再写一次，存储仍不可写时返回明确错误，可写后先写入结果再只补本地，不登录、不重提改密；恢复与后台写入互斥：写入并通知完成前，重试、放弃和再次恢复都被拒绝，只写入并通知一次。保留结果写入仍走上面的 runner 比较，不能复活已放弃或已被新意图取代的任务。

边界：短暂锁或长时间不可写只要进程存活，确定结果都在；进程正常停止（卸载／关闭）或被强杀时，没被存储接受的结果随进程丢失，重启后按提交前的标记成为暂停未知（归 #76 核验），不重发。这与“进程仍活着却主动丢弃”的旧行为不同。重启将遗留 submitting 归为未知；prepared／preparing 不自动继续远端；只自动补做已持久记录成功的本地提交。硬杀发生在远端响应与结果落盘之间时，只能按提前保存的未知标记保守暂停。若磁盘连结果本身都不能持久化，不能承诺重启仍知道那次成功；不因此丢意图或自动重发。

已知余量（均保守、不重发远端）：删除群逐个账号写入，若恰有改密本地提交插入其间，凭据比较交换会以409中止并留下部分账号已移除该群（仅收窄开放范围），重新删除即可完成；放弃、取消、恢复不绑定选择者，仅要求当前主人或已鉴权后台。

协程取消与线程事务取消不同：`to_thread` 内已开始的 SQLite 事务不能撤回，调用者取消后确认可能仍落盘为 prepared，但绝不会由那个线程提交网络。协议任务的最终落盘／本地提交有独立屏蔽清理；重复取消不会打断它。通知最多等待10秒，失败不会改写已确定远端／本地结果。插件卸载先取消并等待任务再关库，关进程仍依赖持久意图。

## 密钥、权限与备份

复用已有 cryptography 的 Fernet 认证加密。`NINJA3_INTENT_KEY_FILE` 指向**外部独立密钥文件**，内容为有效44字节 Fernet key；不自动生成、不通过聊天／HTTP接收、不写数据库／仓库。只接受当前运行用户所有、非符号链接、组和其他用户无权限的普通文件。目录也应仅运行用户可进入，主机／容器密钥挂载独立于源码与数据库备份。测试密钥仅在 pytest 临时目录生成，绝非生产密钥。

密钥缺失、权限不符或错误：确认事务回滚、不开始新改密；已有未知／待本地提交任务保持暂停，不换新密码补救。恢复需要原密钥与对应数据库。不得在活动意图期间直接更换密钥，当前不实现轮换。密钥和数据库应分别加密备份并验证配套可恢复；备份／复制 SQLite 使用一致性备份或停写检查点，不遗漏 WAL。只持有数据库的读者不能解密待用意图；数据库加密不防同一进程内存、运行账号被攻陷或同时取得密钥。

新数据库文件以0600创建，新增末级目录以0700创建；已有数据库、父目录、WAL/SHM及备份权限由部署者核对，本轮不改生产权限。**正式账号记录仍沿用 #72 的 accounts.password 明文存储，成功提交后该正式密码会出现在数据库／WAL；本票没有把整个账号库改成密文。** 因此数据库、WAL、旧备份和导出都必须作为完整凭据保护，不可只保护新意图列；需要全库加密时由部署层加密磁盘／备份承接。

## 查询接口与组合点

公开窄接口：`Ninja3.account_paused(bot, account_id)`；读取当前持久任务暂停，不可读即暂停。`password_tasks.query_current(bot, account_snapshots)` 在发送前同步核对当前暂停与账号精确快照，防止“读取旧密码→改密已完成且恢复→发送旧密码”。SQLite只读连接的 busy_timeout=0，遇锁或不可用立即拒绝，不做网络等待。普通目录和文本查询已接入。

给 #74 的必要补丁位置（未合入其候选、未复制菜单）：菜单创建／点击解析候选时过滤 `account_paused`；所有异步鉴权和准备完成后、实际 `sender` 调用前，同步调用 `query_current`（列表传本次快照列表，单条传该快照），并保留 #74 自身点击者／菜单代际／授权最终门。失败返回“账号或授权刚刚变化”。不要在该检查与发送之间新增 await。#73 若调整 service.py 的共同最终门，须保留上述守卫；最终由总控在实际组合树验证。

## 真实身份字段仍待核对

静态核查已交付 #70 正文、原件与仓库文档，没有可证明真实 userinfo 字段的响应结构。当前协议严格要求 userinfo.data 的完整字符串 phone／area 与授权意图一致。账号记录没有地区字段，意图固定 area=`86`（与 #70 原件默认一致），非86手机号账号会在身份核对处失败关闭；缺失／掩码／类型不符立即停止，假平台测试不代表真平台验证。

待来源方确认的问题：**已验证账号中心 `GET /api/web/user_center/userinfo` 成功时，`data` 中可用于绑定目标账号的稳定身份字段的精确路径、类型是什么？是否有完整手机号和地区，或仅稳定用户ID／掩码？请只给字段名、类型及人工替换值示例，例如 `{"data":{"某字段":"TEST_ACCOUNT_ID"}}`，并说明与登录手机号关联的验证依据。不要提供真实手机号、Cookie、令牌、动态密钥或原始响应。**

该字段契约是实际接线／发布缺口。不得删身份检查、拿请求中的 phone 回填服务端身份，或用一次登录成功代替核对。本地离线能力不等于真实改密入口已获验收。
