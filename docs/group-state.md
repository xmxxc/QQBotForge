# 群状态模块

对应 #21—#23；独立安装 `modules/group_state/` 完整目录，在模块管理中启用“群状态”。不需要安装授权、问答或账户扩展。数据在该目录的 `data/group-state.db`，使用与其他扩展相同的 SQLite v1 记录格式。

框架最低需要 F01 `460c841` 的本地恢复 v1、上游 `b410938` 的群生命周期／连接事实及 `before_event` 接收入口。本轮验证基线为 personal `f797ead`（已合入 #38／#39 的框架恢复与 Hook 接线）与本业务目录的真实合并候选；不能仅在旧框架里手工 emit Hook 代替验证。

已登录后台打开“群状态”，选择 Bot，查看已知群，或输入群原生标识刷新 Bot 在群状态。QQ 主人可发：

```text
群状态
群状态 刷新 <群原生ID>
```

私聊显示详情；群里只给状态并引导到主人私聊／后台。普通成员不能枚举群状态，写请求沿用后台会话和同源校验。Bot 的身份和群原生标识作为分区依据，展示名不能代替标识。

已知群来自实际收到的原生群事件或主人显式刷新，界面与接口始终标明 `scope=known`、`complete=false`。不把记录总数称为平台所有群。刷新复用框架 `get_group_bot_state(return_error=True)`，只接受完整可识别的平台结果。接口许可、错误、历史状态和核验时间分别显示；查询失败、空值或未获许可不表示 Bot 已离群。历史 `bot_state` 在 `reliable=false` 时只能作历史参考。重启／重载保留历史，但先标记 `process_restart`，须重建恢复基线。

消费者从运行模块取得 `await group_state.snapshot(appid)`、`await group_state.refresh(appid, native_group)` 和 `group_state.capabilities()`，不要读取内部 SQLite。快照是独立副本，含 Bot、模块代际、版本、每群来源／核验时间和可靠性。进入核验与核验完成分别递增版本；不同模块代际的版本不能混用。刷新时收到同群新事实会拒绝旧结果；模块卸载后旧请求不能继续确认当前状态。冷加载与等待读取锁的在途请求同样会失效：直接消费接口抛出 RuntimeError，已进入路由的 HTTP 读取返回 503；不会返回或缓存旧代际历史快照。重新启用后由新实例加载历史并重新核验。

人工确认在等待提交前就递增群版本，使旧名册与分页凭据失效，并把目标成员保留为不可靠历史；失败或取消不能恢复旧证明，取消标记为 `confirmation_cancelled`。重新确认只恢复该成员，完整名册仍须单独重新核验。

刷新、名册、单人核验与人工确认都以独立候选提交数据库，提交等待期间快照保持进行中的不可信状态。提交成功后再次检查模块是否仍启用及同群版本是否改变，再发布结果；卸载后返回存储不可用，不返回旧实例的完整／可靠事实。提交失败保留上一份事实作历史，该群、名册与成员标为 `persistence_failed`，修复存储后可直接重试。同群的新观察在等待写入时立即失效旧结果。取消请求时等待其数据库线程实际结束，再释放写入顺序锁和报告取消，避免迟到写入覆盖新观察。模块停止先撤销实例有效性，再异步等待 SQLite 在途操作与关闭，避免阻塞其他 Bot 和后台请求。启用过程中途失败或取消时，候选实例撤销本次注册的 before_event 回调、路由与页面并关闭存储；路由已被其他处理器替换时不删除，其他模块的页面和路由不受影响。连接恢复／连接状态订阅在任一步失败或取消时，只撤销已取得的通知、订阅与存储，保留原始异常；重复关闭无副作用。

群事件观察落库失败时，相关历史标记 `persistence_failed`，群内主人查看／刷新命令会收到存储错误提示。普通消息与未授权命令继续原消息链，错误提示仍受当前 Bot 主人及黑名单检查。失败只标记本次写入所携带且尚未落库的群；迟到的写入失败不会覆盖更新的同群事实，其他群与其他 Bot 不受影响。主人命令一经识别即被本模块消费：回复发送抛出异常时只记录警告，不重发结果未知的消息，也不把该命令交还普通插件或默认回复。

首次保存失败或排队取消也会结束刷新、名册及单人核验并保留历史；刷新取消后标为 `historical`、`refresh_cancelled`，名册与单人核验被取消或查询异常时同样标为 `roster_cancelled`／`verification_cancelled` 等，不留下进行中标记。首次保存尚在写锁队列中时取消，使用上述操作对应的 `*_cancelled`；若已进入 SQLite 写入，线程排空后首次保存会先将相关事实保守标为 `persistence_failed`，外层清理不覆盖该更新版本。两者都使旧证明失效，需重新核验。失败或取消的清理只修改仍属于本次操作的群版本，不能覆盖新的原生观察。平台字段类型异常按不可识别响应处理，返回 `response_unknown`，不发布可信状态。页面切换 Bot、修改群标识或发起新请求时清除旧结果与成员分页，只有当前 Bot、当前群的最新请求的成功或错误响应可以更新页面。

G01 提供已知群概览与 Bot 状态，G02（#22）补充分页名册及单成员核验，G03（#23）提供成员周期和恢复订阅。本模块不存功能授权、绑定或账密。新发现的群／成员使相关事实版本失效；已知成员普通聊天不重复改写成员周期，不将消息视为完整名册或连续性证明。

自动验证使用真实 ModuleManager 独立发现／启停／重载、Application 接收入口、鉴权 HTTP 与 QQ 主人命令，并检查多 Bot、错误保留、刷新中变更及路由卸载。存储故障回归使用临时 SQLite 触发器与写锁，验证失败后不发布可信事实、提交等待期间的新观察、最终保存期间重载及关闭时事件循环可继续运行。使用临时数据库、假身份和平台查询／发送替身；框架版本证据见 #20。浏览器因当前会话没有可用浏览器未完成，真实平台许可未核查，未迁移生产数据。


## 成员、角色与名册完整性（G02）

主人后台使用“刷新完整分页名册”“查看已知成员”“自动核验单人”及有依据的人工确认。QQ 命令：

```text
群状态 名册 <群原生ID>
群状态 核验 <群原生ID> <成员原生OpenID>
群状态 确认 {"group":"假群","member":"假成员","evidence":"主人已核对当前在群","member_role":"member"}
```

人工确认只形成该人的有来源事实；角色未知可传 null，不能代替全群名册。群中命令只给简短处理状态，名册详情留在主人私聊或后台。

稳定消费接口：`sync_roster(bot, group)` 返回本轮名册报告；`verify_member(bot, group, member)` 返回单人核验；`members(bot, group, cursor='', limit=30, version=None, generation=None)` 分页读取已知事实；`confirm_member(..., evidence=..., member_role=None)` 用于已鉴权主人管理。后续页必须携带前页的版本与代际；`next_cursor` 是不透明凭据，只对签发它的 Bot、群、代际与版本有效，换 Bot／群或变化后从第一页重读；持久化期间不签发分页凭据，稍后从第一页读取。HTTP 对应 `/roster`、`/member`、`/members` 和 `/confirm-member`，沿用同一会话／同源鉴权。

平台适配器复用框架公开 `sender.get_json` 读取原始分页及单成员接口。没有使用 `get_group_members` 的补默认值结果作证明，因为该包装会为缺失字段补 `members=[]` 和 `next_cursor=''`，不能判断响应是否真的包含末页标记。每页最多 30 人、每轮最多 1000 页、每次请求 10 秒上限；空值、异常、无许可、中断、重复成员／游标、缺页和未知角色均返回不完整及原因，不推断离群。

完整证明要求显式读到末页、角色可识别、没有遗漏已知未离群成员，且本轮 `bot_state.member_openid` 对应本 Bot 出现在名册中并且角色一致。其他 Bot 及身份类型未知的接收者也保留，不按 bot 标记过滤。没有可靠的本 Bot 群内原生身份时返回未知，不用 AppID、QQ 号或跨群标识凑出身份。

历史成员与本轮名册分别保存。已知成员缺失标记 `known_member_missing`，保留缺失名单及历史，不直接删人。名册结束（成功、已知成员缺失、平台失败、冲突、取消或期间变化）后，本轮置为进行中的成员都转为 `historical` 并带结束原因（如 `known_member_missing`、`timeout`、`permission_denied`、`pagination_conflict`、`roster_cancelled`、`state_changed`），不再显示 `roster_refreshing`；期间已被新观察或单人核验替换的成员保持其较新事实。已离群（`status=left`）成员不计入已知成员，名册进行中及结束后都保持离群历史。个人核验成功或失败、角色变化、新观察及重载都会使旧名册证明失效。完整名册不授予功能资格，也不承诺未投递变化、无穷离线期间或查询／发送原子一致性。

### 字段可信度与部分结果

- 只有 `roster.complete=true` 且其 `version` 与群当前版本一致时，`roster.members` 才可作为全群接收者名单；否则 `roster.members` 只是本轮观察，用于展示和排查。
- 成员记录的 `reliable=true` 是唯一允许单独使用的成员事实。单纯中断（超时、无许可、查询失败、不可识别页、本 Bot 身份查询失败或无效）时，已读到且格式完整、角色可识别的行与完整名册中的同一行同等可信，记为 `platform_roster`；未读到的已知成员转为历史。
- 数据冲突（重复成员、游标循环或空页续页、达到 1000 页上限仍未结束、`bot_state` 所指本 Bot 不在完整读取的名册中或角色矛盾，原因 `pagination_conflict`／`pagination_limit`／`bot_identity_conflict`）使整轮结果不能作为任何成员的资格依据：不写入本轮成员行，已知成员转为历史，原有可靠事实不恢复，需重新核验。
- `reliable=false` 的 `member_role`、`bot`、`joined_at` 只作历史参考。授权消费者（A01 起的受众核验）在名册不完整时只使用 `reliable=true` 且 `status=present` 的成员，并经 G03 提供的 `fact_current` 复核版本后使用。

### 局部重试、分页失效与 G03 依赖

失败只退休本次写入携带且尚未落库的事实；其他群、其他 Bot 不被隔离，修复后对同一群或成员重新执行即可。单人重试只恢复该成员，不重建整群完整证明。任何同群事实变化都会递增群版本，使旧 `next_cursor` 及旧完整证明一并失效，需从第一页重读。重启／重载后全部事实保留为 `process_restart` 历史。

G02 不判断退群：错误、缺页或缺失都不表示成员离开，`status=left`、成员周期、离线期间变化的恢复及消费通知由 G03（#23）提供。只有 G02、未合入 G03 时，名册证明不覆盖两次核验之间未观察到的退群／重进，消费者不能把它当作连续成员资格。

页面状态行逐项标注“完整／已核验／进行中／待核验／未知／历史（原因）”，原始字段仍在下方显示。

持久化未完成时，公开快照和分页接口不发布完整证明，分页接口也不签发凭据；持久化失败时名册证明失效，修复存储后重新核验即可恢复。SQLite 事务不会把失败写入视为成功。该行为用临时 SQLite 写锁和触发器经公开 HTTP／快照验证，未替换存储实现。这些事实通过 G03 接入恢复确认和消费通知；存储重试不会跳过恢复基线与消费完成屏障。

G02 先前 `95b0505` 的框架组合有 153 项业务回归通过，但独立复审仍发现人工确认失败关闭、首次写入排队取消及改群往返页面竞态三项缺口。当前补丁逐项修复并添加回归；精确 SHA、测试组合和同步结果见本轮集成审计报告。既有及新增测试覆盖独立加载、两 Bot／群、多页完整、缺页／重复／中断／角色缺失／本 Bot 缺失、已知成员冲突、并发新观察、个人核验和人工确认、旧分页失效、跨 Bot／群分页凭据、最终写入期间卸载、排队读取跨卸载、查询取消、写入失败后重试及持久化延迟。浏览器无可用实例，未执行视觉核查；真实 QQ 及其平台许可未核查。

页面请求顺序回归执行实际页面脚本，使用 DOM／fetch 替身；运行 `node --test tests/bot_modules/test_group_state_page.cjs`，无需 npm 依赖。群状态 pytest 会在可用时调用该测试，没有 Node.js 时仅跳过页面脚本测试。这些脚本测试不替代浏览器视觉核查。


## 生命周期、消费凭据与恢复（G03）

仅通过 `ctx.subscribe_recovery_events` 接收四类群／成员进出事件，不重复通过普通生命周期订阅写状态。原生群、成员、操作者、事件 ID、时间、序号和连接上下文保存在历史及只读通知中。平台目前没有公开角色变更事件，模块报告 `role_events=not_supported`，角色在可靠查询／主人有依据的核验中更新。

原生事件 ID 的相同载荷最近 256 条去重；同 ID 冲突、迟到、同秒冲突、缺 ID／时间／原生身份均要求重新核验，不靠到达先后来复活成员。离群终态与周期在重启后保留；重入新建周期，核验角色不会恢复旧周期。旧事实仅有人工确认时间时，首次平台查询发现更晚的入群时间也切换周期，不能把离线期间重新入群当作原周期。平台返回早于已知离群时间的入群日期只保留历史。查询不是无限离线事件日志，无法发现平台未投递的变化。

模块 setup 会广播 `group_state_available`（参数为该实例）；晚启用或重载时消费方可重绑通知订阅。已运行消费方首次安装应同时查询 ModuleManager 当前实例。该可用性通知不代表基线或事实已可信。

消费方用 `await state.fact(bot, group, member=None)` 取得事实凭据（需要一次核对全群时用 `await state.facts(bot, group)`，从同一公开副本返回群凭据与逐成员凭据，成员凭据不含群副本），使用前再次执行 `state.fact_current(proof)`。`usable` 包含模块代际、群版本、恢复进度版本、真实写入者版本、持久化／消费完成和来源就绪状态；它只说明事实可用，不授予功能资格。成员事实还须按 `status/state` 区分在群与已离群。`reason` 说明 `usable=false` 的原因：`recovery_processing`（可信补发边界或消费通知尚在完成）与 `persistence_pending`（事实写入尚在完成）都只需稍后重试；`recovery_required` 须重建基线；`unverified` 表示该群／成员事实本身不可靠，详见 `member`／`group_state`；可用时为空串。快照、核验和名册结果在恢复未完成时不报告可靠／完整。

`state.subscribe(async_callback, timeout=5.0)` 发布持久化后的事实变化和连接转换；回调收到递归只读的 Bot、群、代际、版本、原因及原生事件信息。返回订阅有 `active`、幂等 `cancel()` 和最近 100 个 `results`，状态为 `success/error/timeout/cancelled/unloaded`。变化先使旧凭据失效，随后保存历史、等待消费通知成功，最后确认框架投递。失败保持暂停直至重建。同 Bot 的正常通知依次排队，跨群事件或连接变化不会把现行回调误作旧写入者。超时或卸载不无限等待不合作回调；仍在运行的真实写入者按安装目录及 Bot 隔离，跨重复重载保留，退出前不能建立基线。消费方不得在回调外启动未被本契约等待的后台写入。

首次 READY、重启、重载、新会话、失败及未知连续性不代表就绪。主人后台点“重建恢复基线”，私聊发 `群状态 恢复`，或调用 `await state.rebuild(bot)`；HTTP 为已鉴权 `POST /api/ext/group-state/rebuild?bot=...`。重建核验已知群 Bot 状态与尚未离群的已知成员，不要求整群名册才能核验单人。当前代际有依据的主人单人确认可作为该人的基线；旧代际或旧恢复轮次的人工记录不直接恢复。未知间隔后的当前在群人工确认建立新周期，不证明间隔内一直在群，不能据此恢复旧明确授权；平台入群时间能证明原周期时可保留周期。期间相关接收、连接变化、写入／通知未完成、旧回调未退出或查询失败都会拒绝旧 checkpoint。返回 false 时须重新核验，不能仅重试确认。

可信同会话 RESUMED 只在固定补发边界及本地相关处理完成后恢复。新在线事件（包括可信的单成员入群／退群）在途时仍保守暂停该 Bot 的凭据，消费通知完成前 `fact` 报告可重试的 `recovery_processing`，不提前宣告就绪；完成后按下述范围恢复。可信、字段完整且顺序成立的单成员入群／退群只改变该成员：递增群版本使旧快照、名册证明与在途核验失效，新成员保持待核验，退群成员保持离群，重入建立新周期；同群其他成员的可靠事实和 Bot 在群状态重新读取后继续可用。冲突、迟到、缺字段等不可信事件仍暂停该 Bot 全部凭据并要求重建；其他 Bot 继续使用。Bot 被移出暂停该 Bot 并要求重建。Webhook、自定义网关及无可信 WS 连续性的来源不能凭同名通知获得持续可信状态。
